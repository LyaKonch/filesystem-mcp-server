# Автоматична публікація документації

## Рекомендована стратегія

Найбільш стабільний підхід:

1. Зберігати **лише джерела** (`docs/source`) і переклади (`docs/source/locale/uk/LC_MESSAGES/*.po`) у git.
2. Генерувати HTML у CI (GitHub Actions).
3. Публікувати артефакти в гілку `gh-pages`.

Це краще за коміт `docs/build` через `pre-commit`, тому що:
- немає зайвих конфліктів у згенерованих файлах;
- збірка відтворювана в чистому середовищі;
- однаковий результат незалежно від локальної ОС/оточення.

## Що вже налаштовано

- Workflow: `.github/workflows/docs-publish.yml`.
- Тригери: `push` у `main`, `docs/code-documentation`, а також ручний `workflow_dispatch`.
- Деплой цілі: гілка `gh-pages`.

### Що де лежить

- `main` / `docs/code-documentation`: тільки вихідні файли документації.
- `gh-pages`: згенерований HTML-сайт (те, що відкриває GitHub Pages).

## Багатомовність

Workflow будує дві версії з одного джерела + перекладів:
- English: корінь сайту (`/index.html`)
- Українська: `/uk/index.html`

Важливо: в цьому підході українська версія не генерується автоматичним перекладом.
Вона підтримується вручну через `.po` файли в `docs/source/locale/uk/LC_MESSAGES/`.

## Якщо хочете саме окрему гілку `docs/publish`

Можна працювати і так:
- вести changes only для docs в `docs/publish`;
- але **публікацію все одно робити CI** в `gh-pages`.

Тобто `docs/publish` — це гілка-джерело змін, а `gh-pages` — гілка-артефакт.
