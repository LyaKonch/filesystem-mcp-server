# Технічне бачення та взаємодія компонентів

Цей документ доповнює API-докстрінги і пояснює, чому система спроєктована саме так, як працює бізнес-логіка, та які алгоритми є ключовими.

## 1. Архітектурні рішення

### 1.1. Тонке ядро + модульні інструменти

- Точка входу [`main.py`](../main.py) виконує тільки orchestration:
  - парсинг CLI;
  - ініціалізація логування;
  - ініціалізація FastMCP;
  - реєстрація tool-модулів.
- Бізнес-функціональність винесена в окремі модулі:
  - [`tools/filesystem.py`](../tools/filesystem.py)
  - [`tools/monitoring.py`](../tools/monitoring.py)
  - [`tools/server_management.py`](../tools/server_management.py)
  - [`tools/file_transfer.py`](../tools/file_transfer.py)

**Навіщо:** це спрощує розвиток системи (можна додавати нові tools без ускладнення entrypoint) і покращує тестованість.

### 1.2. Security-first модель доступу до файлової системи

- Всі операції з шляхами проходять через [`utilities/dependencies.py`](../utilities/dependencies.py):
  - нормалізація шляху (`check_path`);
  - валідація типу файлу/папки (`validate_path`);
  - контроль дозволених root (`withinAllowed`).
- Доступ обмежений білим списком root-теки (server roots + client roots).

**Навіщо:** захист від випадкового або зловмисного доступу за межі дозволеного контуру.

### 1.3. Єдина межа обробки помилок

- Будь-який tool реєструється через `tool_error_boundary(...)` з [`utilities/error_handling.py`](../utilities/error_handling.py).
- Помилка:
  - логується з `error_id`/`trace_id`;
  - повертається у локалізованому форматі (uk/en);
  - має recovery-підказки для користувача.

**Навіщо:** стабільний формат помилок для клієнтів і швидка діагностика для підтримки.

### 1.4. Централізоване structured logging

- Логування зібрано в [`utilities/logging.py`](../utilities/logging.py).
- Контекст (`request_id`, `trace_id`, `user_id`, `operation`) прокидується middleware і custom-route.
- Підтримано:
  - stdout/stderr розділення за рівнями;
  - ротація файлів;
  - webhook для CRITICAL подій.

**Навіщо:** трасованість інцидентів і прозорість поведінки сервера в продакшн-середовищі.

## 2. Бізнес-логіка

### 2.1. Основна цінність продукту

Сервер надає безпечний MCP-інтерфейс для:

- файлових операцій у межах дозволених директорій;
- моніторингу системи;
- runtime-керування доступними root-теками.

Тобто користувач отримує контрольовану автоматизацію без прямого shell-доступу до всієї системи.

### 2.2. Ролі та доступ

- Режим без auth (`--no-auth`) — зручний для локальної розробки.
- У режимі auth:
  - middleware перевіряє автентифікацію;
  - адмінські tools (tag `admin` / `dangerous`) можуть бути приховані або недоступні.

Ключові модулі:

- [`auth/auth.py`](../auth/auth.py) — побудова auth provider.
- [`auth/auth_middleware.py`](../auth/auth_middleware.py) — контроль доступу на рівні запитів.
- [`auth/permissions.py`](../auth/permissions.py) — визначення ролі й прав користувача.

### 2.3. Операційна бізнес-поведінка

- Користувацькі помилки мають бути зрозумілими, але не розкривати зайві технічні деталі.
- Критичні події повинні мати ID для ескалації.
- Будь-яке «небезпечне» видалення потребує явного підтвердження (`confirm=True` або elicitation).

## 3. Важкі для розуміння алгоритми

### 3.1. Алгоритм перевірки доступу до шляху

Функція `withinAllowed(path, ctx)`:

1. Формує об'єднаний список root-теки.
2. Нормалізує запитаний шлях.
3. Для кожного root пробує `path.relative_to(root)`.
4. Якщо хоча б один root підходить — доступ дозволено.

**Складність:** O(R), де R — кількість root-теки.

**Ризик, який закриває:** path traversal і звернення до несанкціонованих директорій.

### 3.2. Аналіз директорії на безпеку

`analyze_directory_security(...)` у [`tools/filesystem.py`](../tools/filesystem.py) виконує багатокроковий pipeline:

1. Обхід дерева файлів (`os.walk`).
2. Агрегація статистик (типи, MIME, розміри, вік файлів).
3. Евристики ризику (підозрілі розширення, executable-файли, патерни назв).
4. Виявлення дублікатів за SHA-256 (для файлів до порогу розміру).
5. Формування risk-score і текстового звіту.
6. Опційно — AI-доповнення, якщо клієнт підтримує sampling.

**Компроміс:** баланс між повнотою аналізу й продуктивністю (обмеження за розміром файлів та кількістю sample-файлів).

### 3.3. Токени завантаження файлів

У [`tools/file_transfer.py`](../tools/file_transfer.py):

- Генерується випадковий URL-safe токен.
- У пам'яті зберігається відповідність `token -> (path, expires_at)`.
- Перед кожним завантаженням виконується cleanup прострочених токенів.

**Компроміс:** простий in-memory підхід без зовнішнього сховища, але токени не переживають перезапуск сервера.

## 4. Взаємодія між компонентами

## 4.1. Потік запуску

1. [`main.py`](../main.py) читає аргументи CLI і налаштування.
2. Ініціалізується логування.
3. Створюється FastMCP server + auth middleware.
4. Реєструються tools із модулів `tools/*`.
5. Сервер стартує в одному з transport-режимів.

## 4.2. Потік типового tool-виклику

1. Запит доходить до FastMCP.
2. [`auth/auth_middleware.py`](../auth/auth_middleware.py) проставляє контекст і перевіряє доступ.
3. Викликається відповідна функція з `tools/*`.
4. Всередині tool-функції відбуваються перевірки шляху/даних через `utilities/*`.
5. Якщо сталася помилка — `tool_error_boundary` повертає стандартизовану локалізовану відповідь.

## 4.3. Потік збереження користувацького звіту про помилку

1. Клієнт викликає `submit_error_report`.
2. З middleware-контексту забираються `request_id/trace_id/user_id/operation`.
3. [`utilities/error_reports.py`](../utilities/error_reports.py) додає запис у JSONL.
4. Клієнт отримує `report_id` для подальшої комунікації з підтримкою.

## 5. Межі та обмеження поточної реалізації

- Токени завантаження — in-memory, без кластера і без персистентності між рестартами.
- Розширений AI-аналіз залежить від sampling capability клієнта.
- Частина адмін/permission-поведінки закладена як база і може бути розширена політиками доступу на рівні тегій tools.
